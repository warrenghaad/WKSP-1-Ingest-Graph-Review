# RWI Image Pipeline Sweep

Date: 2026-03-21

## Purpose

This sweep answers a narrow question:

- What already exists in the backend for text ingest, tagging, image sourcing, candidate curation, AI prompt construction, approvals, and storage?
- If Replit is used, what should it do without becoming a second canonical RWI/NASH system?

## Executive Call

- Your app is already the canonical operational system for RWI and NASH.
- Supabase is already the real persistence layer for content, sources, needs, image candidates, approvals, and media metadata.
- Replit makes sense only as a first-run worker:
  - read text
  - break it into atomic concepts
  - generate search queries
  - propose AI prompts
  - optionally call your existing endpoints
- Replit should not become the canonical DAM, RWI queue, or approval system if the app already owns those responsibilities.
- Notion is not currently a first-class runtime persistence target in the image pipeline. It appears as separate tooling, not as the live RWI image path.

## Hard Guardrails

- Replit is a worker, not a source of truth.
- Supabase remains the canonical store for approved records, queue state, and lineage.
- Successful images should be persisted to Supabase first.
- Notion should only receive selected or approved outputs, not raw candidate churn.
- Raw research text and ingest artifacts must stay separable from rewritten lesson copy.
- Candidate sets and approvals must remain separate objects.
- AI-generated images must be explicitly marked as generated, not blended with sourced artifacts.
- Image search, approval, and generation should stay tied to lesson, section, and needs scope.
- Immediate source-and-curate behavior should begin from ingest, but approval remains a later gate.

## Replit Role That Makes Sense

Use Replit as a thin first-run textreader and prompt worker.

It should do only these jobs:

- accept pasted research brief, excerpt, or raw copy
- split it into atomic visual concepts
- extract probable entities and tags
- produce:
  - open-web search queries
  - Pinterest-style search phrases
  - museum queries
  - AI ultra-real image prompts
  - diagram prompt specs
- optionally call the app endpoints:
  - `POST /api/research/ingest`
  - `POST /api/rwi/images/ingest-content`
  - `POST /api/rwi/images/search`
  - `POST /api/images/spec/diagram`
  - `POST /api/images/generate/openai`
  - `POST /api/images/generate/gemini-image`

It should not own:

- approvals
- final asset registry
- needs state
- graph linkage
- lesson linkage
- candidate persistence
- canonical binary storage

## Recommended Canonical Flow

### Phase 1: first-run read

- Replit or in-app textreader accepts raw text.
- It returns atomic concepts, search queries, AI prompts, and provisional tags.

### Phase 2: canonical ingest

- Push the result into app endpoints.
- Persist `source` and `content_item`.
- Create or update `rwi_needs`.

### Phase 3: sourcing and curation

- Trigger:
  - `/api/rwi/images/ingest-content`
  - or `/api/rwi/images/auto-search-needs`
  - or `/api/continuous-ingestion/run-once`
- Store candidate sets in Supabase.

### Phase 4: approval

- Approve selected image or generated diagram through `/api/rwi/images/approve` or diagram approval path.
- Persist selected asset metadata into `media_assets` and approval tables.

### Phase 5: optional mirror

- After approval, mirror selected assets to Notion if desired.
- Do not mirror raw candidate noise.

## What Looks Most Canonical Right Now

If one path has to be favored immediately, favor this:

- `/api/rwi-unified/*` as the intended direction
- backed by:
  - `/api/research/ingest`
  - `/api/rwi/images/*`
  - `/api/images/*`
  - `/api/continuous-ingestion/*`
  - Supabase tables in `dao.js` and `sql/rwi-clean.sql`

This is the least disruptive way to get a Replit first-run worker without creating a second platform.
