# Replit Storage Contract

Date: 2026-03-23

## Why This Exists

The missing piece is not just Replit's behavior. The missing piece is where the information goes once Replit starts ingesting, sourcing, curating, and spec'ing.

Replit is handling the image side of RWI. That means it needs a storage contract.

## Core Rule

Replit may organize and hold temporary working state, but the canonical records must be organized into the existing app stack.

That means:

- Replit owns temporary session state
- PostgreSQL and Supabase own canonical runtime records
- the graph layer owns graph-ready node structure
- Notion serves as the CMS, workflow, validation, and checking layer

## What Replit Is Storing Locally

Replit may store temporary local state for:

- draft sessions
- uploaded file references
- extracted text blocks
- concept cards
- draft search queries
- draft AI prompts
- draft overlay specs
- draft pattern specs
- draft hover cards
- candidate cards before handoff

This local state is temporary working memory, not canonical project truth.

## Canonical Storage Targets

### 1. Raw ingest and source records

Canonical target:

- `sources`
- `research_documents` when batch research ingestion is involved

Purpose:

- preserve the original source text or file lineage
- preserve citation, URL, and provenance
- preserve extracted text without losing the original reference

Replit should not be the long-term home of raw ingest.

### 2. Normalized content records

Canonical target:

- `content_items`

Purpose:

- store normalized excerpts, notes, lesson fragments, or ingested content blocks
- connect research text to downstream lesson and section work
- carry section and lesson scope

If Replit ingests a passage, that passage should become a canonical content or source-linked record in the main backend.

### 3. Image needs records

Canonical target:

- `rwi_needs`

Purpose:

- one record per actual image, diagram, overlay, or visual requirement
- tie the need to lesson file, section, artifact, and source row
- hold prompts, overlay notes, diagram prompts, and status

This is the main organizational table for the image side of RWI.

Replit should create or update `rwi_needs` as soon as it knows what the visual need is.

### 4. Candidate set storage

Canonical target:

- `rwi_image_candidate_sets`

Purpose:

- store grouped search results for each artifact or visual need
- preserve the exact query used
- preserve related sources and raw results
- keep candidate churn separate from final approvals

Replit should not treat candidate cards as final assets.

### 5. Search and provider tracking

Canonical targets:

- `image_provider_cache`
- `image_search_log`

Purpose:

- cache repeated searches
- reduce duplicate provider calls
- record which provider, which query, and which candidate was selected

This is where the sourcing behavior becomes traceable.

### 6. Vision and review storage

Canonical targets:

- `image_quality_scores`
- `image_review_queue`

Purpose:

- store fidelity analysis
- store quality scores
- store reasons an image is weak, mismatched, or escalated
- preserve human-in-the-loop review state

This is where the Vision AI layer belongs as data, not just UI.

### 7. Approval storage

Canonical target:

- `rwi_image_approvals`

Purpose:

- store the selected or approved image decision
- preserve the approval payload and scope
- separate reviewed approval from raw candidate noise

This is where approved image choices become authoritative.

### 8. Final asset registry

Canonical target:

- `media_assets`

Purpose:

- store the approved final asset record
- preserve curation method, confidence, reviewer, and timestamps
- connect approved images to content items and lesson surfaces

Replit helps get an image here. Replit does not replace this table.

### 9. Graph and Neo-facing structure

Canonical target:

- `graph_nodes`
- graph-ready packets from the vision and ingest layers

Purpose:

- organize ingested material, concepts, overlays, and elements into graph-facing structure
- align image work with the wiki-graphnode direction
- connect source documents, research concepts, geometric elements, and image assets

Replit should emit graph-ready packets, but the main backend should own the actual graph persistence.

### 10. Notion CMS and workflow layer

Canonical target for workflow and editorial control:

- Notion pages and databases

Purpose:

- CMS organization
- workflow setup
- validation checklists
- editorial and reviewer status
- approval visibility
- publishing readiness
- lesson-facing production views

Notion should hold workflow-facing records, summaries, statuses, and checks.

Notion should not replace the runtime tables for raw candidate blobs, search telemetry, final media metadata, or graph packets.

## The Organization Keys Replit Must Use

Every ingest and image record should organize around the same core keys:

- `grade`
- `week`
- `section`
- `lesson_file`
- `lesson_id`
- `artifact`
- `artifact_id`
- `artifact_key`
- `source_row_index`
- `row_key`
- `source_type`
- `accuracy_status`
- `review_decision`
- `needs_overlay`
- `needs_diagram`
- `content_item_id`
- `needs_id`
- `media_asset_id`
- `graph_node_id` if graph persistence occurs later

These keys are what make Replit's organization compatible with your current backend instead of creating a second schema.

## What Replit Must Do On Ingest

When Replit ingests text or files, it should do this:

1. create local draft session state
2. write raw source lineage into canonical ingest or source records
3. write normalized content into `content_items` or linked ingest records
4. derive visual needs and create or update `rwi_needs`
5. create graph-ready packets for concepts, overlays, patterns, and hover cards
6. run sourcing and store grouped candidates in `rwi_image_candidate_sets`
7. run vision fidelity and store review or quality outputs in the review and scoring tables
8. on approval, write the selected decision to `rwi_image_approvals`
9. write approved final asset records into `media_assets`
10. update Notion workflow records during the pipeline for status, validation, and checking
11. mirror approved or publish-ready outputs into the relevant Notion CMS surfaces

## The Replit Rule For RWI

Replit is the image-side worker in RWI.

That means it is responsible for:

- sourcing
- curating
- spec'ing
- fidelity checking
- organizing temporary working state
- writing into the canonical image and content tables

It is not responsible for inventing a second storage model.

## The Simplest Version

Replit may manage the workflow, but the information should land here:

- raw source -> `sources` or research ingest records
- normalized text -> `content_items`
- image need -> `rwi_needs`
- search results -> `rwi_image_candidate_sets`
- search/cache telemetry -> `image_search_log` and `image_provider_cache`
- fidelity and review -> `image_quality_scores` and `image_review_queue`
- approval -> `rwi_image_approvals`
- final approved asset -> `media_assets`
- graph-facing packet -> `graph_nodes` or graph-ready backend packet
- workflow and CMS layer -> Notion

That is the storage contract Replit should follow right now.
